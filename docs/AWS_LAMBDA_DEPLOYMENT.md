# Deploy TaskHub backend to AWS Lambda

This backend is a Spring Boot 3 API. For AWS Lambda, the project uses
AWS Serverless Java Container to adapt API Gateway proxy requests into the
existing Spring MVC controllers.

## What was added

- Lambda handler:
  `BE/src/main/java/com/taskhub/lambda/StreamLambdaHandler.java`
- API Gateway stage path handling: the Lambda handler normalizes API Gateway
  paths like `/Prod/api/health` to Spring MVC paths like `/api/health`.
- Public health check endpoint:
  `BE/src/main/java/com/taskhub/controller/HealthController.java`
- AWS Lambda dependencies and shaded JAR build:
  `BE/pom.xml`
- AWS SAM template:
  `BE/template.yaml`
- Lambda artifact generated by Maven:
  `BE/target/taskhub-backend-1.0.0-lambda.jar`

## Prerequisites

Install and configure these on your machine:

1. AWS CLI
2. AWS SAM CLI
3. Java 21
4. Maven, or the local Maven already included in this repo
5. AWS credentials with permission to deploy Lambda, API Gateway, CloudFormation,
   IAM roles, and CloudWatch Logs

Check AWS identity:

```powershell
aws sts get-caller-identity
```

## Deploy with AWS SAM

From `Taskhub_BE/BE`:

```powershell
sam deploy --guided
```

If `sam` is not yet on `PATH` in the current terminal:

```powershell
& "C:\Program Files\Amazon\AWSSAMCLI\bin\sam.cmd" deploy --guided
```

This repo includes `BE/samconfig.toml` with the fixed deploy settings:

```text
stack_name=taskhub-backend
region=ap-southeast-1
capabilities=CAPABILITY_IAM
```

Secrets are intentionally not stored in `samconfig.toml`. For faster deploys
after the first run, pass only the required secret parameters:

```powershell
sam deploy --parameter-overrides `
  SpringDatasourcePassword="<Supabase database password>" `
  AppJwtSecret="<at-least-32-character-secret>" `
  SupabaseUrl="" `
  SupabaseServiceRoleKey=""
```

## Environment used by Lambda

The SAM template sets:

```text
JAVA_TOOL_OPTIONS=-XX:+TieredCompilation -XX:TieredStopAtLevel=1
SPRING_PROFILES_ACTIVE=supabase
SPRING_DATASOURCE_URL=jdbc:postgresql://aws-1-ap-southeast-1.pooler.supabase.com:5432/postgres?sslmode=require
SPRING_DATASOURCE_USERNAME=postgres.wwduzspwejdyvbnjxkkz
SPRING_DATASOURCE_PASSWORD=<SAM parameter>
SPRING_JPA_HIBERNATE_DDL_AUTO=validate
SPRING_JPA_SHOW_SQL=false
SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=2
SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE=0
SPRING_DATASOURCE_HIKARI_CONNECTION_TIMEOUT=30000
APP_JWT_SECRET=<SAM parameter>
```

The database URL uses the Supabase Session Pooler because the direct Supabase
database host was not reachable reliably from the local network, while the
pooler host tested successfully on port 5432.

The Lambda memory is set to 3008 MB, which was the maximum accepted by the
current AWS account/runtime during deployment. The JVM option above reduces Java
cold start work by limiting tiered compilation during startup.

Hikari is limited to a small pool because Supabase's session pooler can reject
too many simultaneous Lambda database sessions with `EMAXCONNSESSION`.

### CORS and Stage Path "Failed to fetch" Gotcha

If the browser displays a `Failed to fetch` error while direct API calls via curl or python return `200`, it is likely due to stage prefix mismatch:
*   **The Issue:** When `VITE_API_BASE_URL` is set to an API Gateway stage endpoint like `https://cyxlrtltrl.execute-api.ap-southeast-1.amazonaws.com/Prod/`, using standard JavaScript `new URL("/api/auth/login", BASE_URL)` strips the `/Prod/` prefix entirely, resulting in `https://cyxlrtltrl.execute-api.ap-southeast-1.amazonaws.com/api/auth/login`. This bypasses the stage prefix and fails with a connection or CORS failure.
*   **The Solution:** The frontend uses `getApiUrl` from `client.ts` to construct API URLs. It strips the trailing slash from `BASE_URL` and appends the prefix and path directly (e.g. `baseUrlClean + API_PREFIX + path`), preserving the `/Prod/` stage prefix.

Swagger UI is configured at:

```text
<ApiUrl>/swagger-ui.html
```

During the first Lambda cold start, API Gateway can return `502 Bad Gateway` if
the Java/Spring initialization exceeds the init window. A second request after
the function is warm should succeed. For production, consider Lambda SnapStart
or provisioned concurrency if first-request reliability matters.

## Production notes

- Keep `SPRING_JPA_HIBERNATE_DDL_AUTO=validate` in production after the schema
  has been created.
- Use a strong `APP_JWT_SECRET` and rotate it if it has been exposed.
- Keep Supabase service role keys only in AWS Lambda environment variables or
  AWS Secrets Manager.
- Spring Boot on Lambda can have cold starts. The template uses 3008 MB memory,
  a 30 second timeout, and Java startup options as a practical starting point.
